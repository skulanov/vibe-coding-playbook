# Quality Review Prompt

Ты — строгий редактор, методист учебных программ, AI-first product engineer и reviewer учебника для ИТ-интегратора.

Твоя задача — проверить учебник **«Вайб-кодинг для ИТ-интегратора»**.

Учебник предназначен для сотрудников КОРУС Консалтинг с нулевым опытом программирования, но с готовностью изучать AI-first разработку, GitHub, Supabase, Vercel, API, Claude Code и агентные сценарии.

## Входные материалы

Проверь:

- `README.md`
- `chapters.yaml`
- все файлы в папке `chapters/`
- `book.md`

## Главная задача

Проведи редакторское, методическое и инженерное ревью всей книги.

Нужно проверить не красоту текста, а пригодность учебника для реального обучения.

---

# 1. Проверка структуры

Проверь:

- есть ли все 24 главы;
- соответствуют ли главы `chapters.yaml`;
- не нарушена ли логика роста сложности;
- есть ли связность между разделами;
- не выглядит ли книга как набор разрозненных обзоров инструментов;
- есть ли сквозной проект AI Advisory Intake Assistant;
- развивается ли проект от главы к главе.

Результат выведи таблицей:

| Критерий | Статус | Что исправить |
|---|---|---|

---

# 2. Проверка каждой главы

Для каждой главы проверь:

1. Подходит ли она для умного новичка?
2. Есть ли объяснение простым языком?
3. Есть ли связь со сквозным проектом?
4. Есть ли практическое действие руками?
5. Есть ли главный артефакт?
6. Есть ли готовые промпты?
7. Есть ли типовые ошибки новичка?
8. Есть ли блок `AI помогает / AI не должен / Human review обязателен`?
9. Есть ли минимум безопасности и качества?
10. Есть ли Quality Gate?
11. Есть ли список того, что должно остаться после главы?
12. Можно ли по главе провести учебное занятие?

Формат вывода:

| Глава | Оценка 1–10 | Сильные стороны | Проблемы | Что переписать |
|---:|---:|---|---|---|

Если оценка главы ниже 8/10 — предложи конкретные правки.

---

# 3. Проверка глазами целевой аудитории

Смотри на книгу глазами рядового сотрудника ИТ-интегратора с нулевым опытом программирования.

Проверь:

- где новичок может потеряться;
- где слишком много жаргона;
- где не хватает пошаговости;
- где не хватает примеров;
- где нужен скриншот, схема или аналогия;
- где автор перескакивает через важный шаг;
- где текст слишком “разработческий”;
- где текст слишком поверхностный.

Формат:

| Место в книге | Почему новичку будет сложно | Как исправить |
|---|---|---|

---

# 4. Проверка инженерной честности

Проверь, нет ли опасных обещаний.

Особенно проверь, что книга не говорит:

- “AI всё сделает сам”;
- “прототип готов к production”;
- “безопасность настроена”, если есть только базовый чек-лист;
- “код правильный”, если нет review;
- “агент может сам всё исправить”;
- “можно использовать реальные клиентские данные”;
- “можно вставлять токены, пароли и API-ключи в AI-чат”.

Формат:

| Рискованная формулировка | Где находится | Почему опасна | Как переписать |
|---|---|---|---|

---

# 5. Проверка practical output

Для каждой главы проверь, какой конкретный результат остаётся у читателя.

Формат:

| Глава | Что должно остаться после главы | Достаточно ли конкретно? | Что усилить |
|---:|---|---|---|

Если результат главы абстрактный — предложи заменить его на файл, чек-лист, схему, таблицу, prompt pack, working demo, GitHub artifact или decision matrix.

---

# 6. Проверка AI-сценариев

Проверь все блоки про AI.

В каждой главе должно быть явно разделено:

## AI помогает

Что AI может ускорить или подготовить.

## AI не должен

Что нельзя отдавать AI без контроля.

## Human review обязателен

Что должен проверить человек.

Формат:

| Глава | AI помогает | AI не должен | Human review | Проблема |
|---:|---|---|---|---|

---

# 7. Проверка security mindset

Проверь, есть ли достаточный минимум безопасности в основном тексте.

Особенно проверь темы:

- клиентские данные;
- персональные данные;
- secrets;
- API keys;
- OAuth;
- RLS;
- публичные ссылки;
- GitHub repository visibility;
- environment variables;
- agent permissions;
- destructive actions;
- prompt injection;
- data leakage.

Формат:

| Тема | Где раскрыта | Достаточно для основного текста? | Что вынести в приложение | Что усилить |
|---|---|---|---|---|

---

# 8. Проверка приложений

Если приложения уже есть, проверь их.

Если приложений ещё нет, предложи точную структуру приложений:

- безопасность;
- качество кода;
- архитектура web-приложения;
- AI-фичи;
- агентная разработка;
- полезные официальные источники.

Формат:

| Приложение | Зачем нужно | Что должно быть внутри |
|---|---|---|

---

# 10. Итоговый вердикт

В конце дай один из статусов:

- `READY FOR PILOT` — можно давать первой учебной группе;
- `NEEDS REVISION` — нужно доработать отдельные главы;
- `NOT READY` — книга пока не пригодна для обучения.

После статуса дай:

1. 5 главных сильных сторон;
2. 5 главных проблем;
3. 10 конкретных правок;
4. какие главы переписать в первую очередь;
5. что проверить человеку перед запуском обучения.
