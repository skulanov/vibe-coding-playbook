# Глава 3. Минимальный технический словарь вайбкодера

## 1. Зачем эта глава нужна

Когда вы впервые открываете документацию GitHub или Supabase, кажется, что там написано на иностранном языке: commit, branch, pull request, deploy, environment variable, RLS, OAuth, agent, hook, prompt...

Страх перед терминами — одна из главных причин, по которым люди без технического бэкграунда бросают AI-разработку на первых шагах. При этом большинство этих понятий объясняются за несколько предложений.

Эта глава снимает барьер. Не нужно знать всё — нужно знать ровно столько, чтобы не теряться в инструкциях и понимать, что происходит в вашем проекте.

После этой главы вы не станете программистом. Но вы перестанете теряться от базовых технических слов и сможете осмысленно работать с AI-инструментами, GitHub, Supabase, Vercel и Claude Code.

---

## 2. Объяснение на человеческом языке

### Как устроен этот глоссарий

Все термины разбиты по смысловым группам. Каждый термин:
- объясняется через бытовую аналогию;
- получает техническое определение;
- привязывается к конкретной точке в AI Advisory Intake Assistant.

Не нужно запоминать всё прямо сейчас. Глоссарий — это справочник, к которому можно возвращаться по ходу учебника.

---

## 3. Как это связано со сквозным проектом

В каждом термине этой главы мы будем показывать, где он встречается в **AI Advisory Intake Assistant**.

Это не абстрактный словарь — это терминология вашего будущего приложения.

### Группа 1. Frontend и backend

---

**Frontend** (фронтенд)

*Аналогия:* Витрина магазина — то, что видит покупатель: полки, ценники, кассы.

*Определение:* Часть приложения, которую видит и с которой взаимодействует пользователь. Это экраны, кнопки, формы, таблицы в браузере или мобильном приложении.

*В AI Advisory Intake Assistant:* Форма для ввода клиентского запроса, список запросов, страница входа — всё это frontend.

*Технология:* HTML, CSS, JavaScript, React, Next.js. В нашем учебнике Lovable и v0 генерируют frontend автоматически.

---

**Backend** (бэкенд)

*Аналогия:* Склад и бухгалтерия за стенкой — то, что работает, но пользователь этого не видит.

*Определение:* Часть приложения, которая работает на сервере: обрабатывает запросы, хранит данные, выполняет логику, проверяет права доступа.

*В AI Advisory Intake Assistant:* Supabase — наш backend. Там хранятся данные о запросах клиентов и сотрудниках.

*Разница:* Frontend показывает данные, backend их хранит и обрабатывает. Если backend выключить — frontend покажет пустые экраны.

---

**Full-stack**

*Аналогия:* Человек, который умеет и работать с витриной, и управлять складом.

*Определение:* Разработка, которая охватывает и frontend, и backend одновременно. Lovable и Bolt.new — full-stack AI-builder'ы: они генерируют и интерфейс, и серверную логику.

*В нашем учебнике:* Когда мы работаем с Lovable — мы делаем full-stack разработку, даже если не осознаём этого явно.

---

### Группа 2. API

---

**API** (Application Programming Interface, интерфейс программирования приложений)

*Аналогия:* Меню в ресторане. Вы делаете заказ (запрос), кухня готовит (обрабатывает), официант приносит блюдо (возвращает результат). Вам не нужно знать рецепт — нужно знать, что заказать.

*Определение:* Способ, которым одна программа обращается к другой. Клиент (ваш код) отправляет запрос на сервер, сервер выполняет задачу и возвращает результат.

*В AI Advisory Intake Assistant:*
- Приложение обращается к Supabase API, чтобы прочитать список запросов.
- Приложение обращается к Anthropic API, чтобы классифицировать запрос клиента с помощью AI.

*Ключевые термины рядом:*
- **Endpoint** — конкретный адрес API, куда отправляется запрос. Например: `api.supabase.co/rest/v1/requests`
- **Request / Response** — запрос и ответ. Вы отправляете запрос, API возвращает ответ.
- **HTTP-метод** — тип действия: GET (получить данные), POST (создать), PUT (обновить), DELETE (удалить).

---

**REST API**

*Аналогия:* Стандартная форма заказа, которую понимают все рестораны одной сети.

*Определение:* Самый распространённый стиль API, основанный на HTTP-запросах. Supabase использует REST API. Простота REST — в предсказуемости: есть адрес (endpoint), есть метод (GET/POST/PUT/DELETE), есть данные в JSON-формате.

*В нашем учебнике:* Когда Lovable подключается к Supabase — он использует REST API под капотом.

---

**JSON** (JavaScript Object Notation)

*Аналогия:* Структурированный список в виде «ключ: значение». Как анкета, где каждое поле имеет название и значение.

*Определение:* Текстовый формат для передачи данных между программами. API практически всегда возвращают данные в JSON.

*Пример* (данные о запросе клиента):
```json
{
  "id": "req-001",
  "client": "ООО Ромашка",
  "topic": "Внедрение ERP",
  "status": "new",
  "created_at": "2025-06-05"
}
```

*В AI Advisory Intake Assistant:* Когда мы вызываем Anthropic API, он возвращает классификацию запроса в JSON. Мы в главе 20 разберём, как с ним работать.

---

### Группа 3. База данных

---

**База данных (database)**

*Аналогия:* Шкаф с папками. Каждая папка — это таблица. В каждой папке — листы с данными (строки). У каждого листа есть поля (колонки).

*Определение:* Организованное хранилище данных. В нашем учебнике — PostgreSQL через Supabase. Данные хранятся в таблицах, строки — это записи, колонки — это поля.

*В AI Advisory Intake Assistant:*
- Таблица `requests` — клиентские запросы
- Таблица `clients` — данные о клиентах
- Таблица `users` — сотрудники, которые работают с запросами

---

**Таблица (table)**

*Аналогия:* Лист Excel с заголовками и строками.

*Определение:* Структура данных в базе. Каждая строка — одна запись (например, один клиентский запрос). Каждая колонка — одно поле (например, «название компании», «дата», «статус»).

*В AI Advisory Intake Assistant:* Таблица `requests` может выглядеть так:

| id | client_name | topic | status | created_at |
|---|---|---|---|---|
| 1 | ООО Ромашка | Внедрение ERP | new | 2025-06-01 |
| 2 | АО Берёзка | BI-аналитика | in_progress | 2025-06-03 |

---

**SQL** (Structured Query Language)

*Аналогия:* Язык для работы с шкафом с папками: «Покажи мне все листы из папки "Запросы" за этот месяц».

*Определение:* Язык запросов к реляционным базам данных. Supabase использует PostgreSQL, и запросы пишутся на SQL.

*В нашем учебнике:* Lovable и Supabase часто генерируют SQL сами. Но понимать структуру запроса — SELECT, WHERE, INSERT — полезно. Глава 10 объяснит минимум.

*Простой пример:*
```sql
SELECT * FROM requests WHERE status = 'new';
```
Означает: «Покажи все запросы со статусом "новый"».

---

**Realtime**

*Аналогия:* Онлайн-таблица, которая обновляется сама, когда коллега что-то меняет — без перезагрузки страницы.

*Определение:* Функция Supabase, которая позволяет получать обновления из базы данных в реальном времени через WebSocket.

*В AI Advisory Intake Assistant:* Если один сотрудник изменил статус запроса, другой сотрудник видит изменение без перезагрузки.

---

### Группа 4. Авторизация (auth)

---

**Authentication (аутентификация)**

*Аналогия:* Проверка паспорта на входе. Кто вы — сотрудник или посторонний?

*Определение:* Процесс проверки личности пользователя. Пользователь вводит логин и пароль (или входит через Google) — система проверяет, кто это.

*В AI Advisory Intake Assistant:* Сотрудник входит по корпоративному email. Система знает, что это Иван из отдела пресейла.

---

**Authorization (авторизация)**

*Аналогия:* После проверки паспорта — пустить в общий зал или в VIP-зону?

*Определение:* Процесс проверки прав: что именно этому пользователю разрешено делать. Аутентификация — это «кто вы», авторизация — «что вам можно».

*В AI Advisory Intake Assistant:* Иван видит только свои запросы. Менеджер видит запросы всей команды. Администратор видит всё.

*Частая ошибка:* Путать authentication и authorization. Приложение может знать «кто вы» (authentication), но не ограничивать доступ к данным (authorization). Тогда любой залогиненный пользователь увидит все данные.

---

**Session (сессия)**

*Аналогия:* Браслет на руке, который вы получили на входе в парк. Пока браслет есть — вы «внутри». Сняли браслет (вышли из системы) — нужно снова проходить на вход.

*Определение:* Временный идентификатор, который создаётся при входе в систему и хранится в браузере. Пока сессия активна — пользователь «вошедший». Когда сессия заканчивается — нужно войти снова.

---

**OAuth**

*Аналогия:* Вход через пропуск другой организации. «Я сотрудник Google — пустите меня». Система проверяет Google-пропуск и пускает.

*Определение:* Протокол, который позволяет войти в приложение через аккаунт другого сервиса (Google, GitHub, Microsoft). Пользователь не вводит новый пароль — он делегирует проверку личности Google или GitHub.

*В AI Advisory Intake Assistant:* Вход через Google-аккаунт — это OAuth. Supabase поддерживает Google OAuth из коробки.

---

**RLS (Row Level Security)**

*Аналогия:* Шкаф с папками, где у каждого сотрудника есть ключ только от своих папок. Даже если знаешь, где стоит шкаф, — чужие папки не откроешь.

*Определение:* Механизм PostgreSQL и Supabase, который ограничивает доступ к строкам таблицы на уровне базы данных. Политика RLS говорит: «Пользователь A может видеть только строки, где `user_id = A`».

*В AI Advisory Intake Assistant:* RLS гарантирует, что сотрудник видит только свои запросы, даже если приложение по ошибке запросит все данные.

*Почему это важно:* Без RLS авторизация в интерфейсе — это «закрытая дверь со стеклянной стеной». Умный пользователь может обойти ограничения интерфейса и прочитать чужие данные напрямую через API.

---

### Группа 5. Git, commit, branch, pull request

---

**Git**

*Аналогия:* Система «сохранить версию», как в Word или Figma, но для кода. Каждое сохранение запоминается с пояснением «что изменилось и зачем».

*Определение:* Система контроля версий. Git отслеживает изменения в файлах, позволяет вернуться к любой предыдущей версии и работать параллельно над разными функциями.

---

**Репозиторий (repository, repo)**

*Аналогия:* Папка проекта с историей всех изменений и возможностью работать совместно.

*Определение:* Место хранения кода и истории изменений. В нашем учебнике репозиторий находится на GitHub. Каждый проект — отдельный репозиторий.

*В AI Advisory Intake Assistant:* Весь код приложения живёт в GitHub-репозитории. Lovable может автоматически создать репозиторий и пушить туда код.

---

**Commit (коммит)**

*Аналогия:* Снимок состояния проекта в конкретный момент с подписью «что изменилось и зачем».

*Определение:* Сохранение набора изменений в Git с сообщением. Коммит фиксирует: кто, что и когда изменил.

*Плохой коммит:* `fix stuff`
*Хороший коммит:* `Add client name validation to intake form`

*В нашем учебнике:* Каждый значимый шаг в разработке должен быть зафиксирован коммитом. Это история проекта.

---

**Branch (ветка)**

*Аналогия:* Копия проекта, в которой можно экспериментировать, не боясь сломать основную версию. Как черновик рядом с финальным документом.

*Определение:* Независимая линия разработки. Основная ветка — `main` — содержит рабочую версию. Новые функции разрабатываются в отдельных ветках и добавляются в `main` после проверки.

*В AI Advisory Intake Assistant:* Мы тестируем новую AI-фичу в ветке `feature/ai-classification`, не трогая рабочую версию.

---

**Pull Request (PR)**

*Аналогия:* Предложение добавить изменения из черновика в финальный документ. Коллеги читают черновик, оставляют комментарии, и только потом изменения принимаются.

*Определение:* Механизм предложения слить (merge) одну ветку в другую. PR — это возможность проверить изменения до того, как они попадут в основную версию.

*В AI Advisory Intake Assistant:* Когда AI генерирует новую функцию в отдельной ветке — вы делаете pull request, проверяете изменения, и только потом merge в `main`.

---

**Merge (слияние)**

*Аналогия:* Принять черновик и внести правки в финальный документ.

*Определение:* Объединение изменений из одной ветки в другую. После того как pull request одобрен — ветка сливается (merge) в основную.

---

**Clone (клонировать)**

*Аналогия:* Сделать полную копию папки проекта на своём компьютере.

*Определение:* Скопировать репозиторий с GitHub на локальный компьютер или в рабочую среду.

---

### Группа 6. Deploy, environment, secret

---

**Deploy (деплой)**

*Аналогия:* Перевезти готовое блюдо из кухни на стол к гостям. Пока блюдо на кухне (у вас локально) — никто не попробует.

*Определение:* Процесс публикации приложения на сервере, чтобы оно было доступно по URL из любого места. Инструмент в нашем учебнике — Vercel.

*В AI Advisory Intake Assistant:* После деплоя сотрудники могут открыть приложение по ссылке без установки чего-либо.

---

**Environment (окружение, среда)**

*Аналогия:* Тестовая кухня и основная кухня. В тестовой — можно экспериментировать. В основной — только проверенные блюда.

*Определение:* Изолированное место запуска приложения с собственными настройками. Стандартные среды:
- **local** — на вашем компьютере, только для вас
- **preview** — тестовая публичная среда, где проверяют изменения
- **production** — основная среда, с которой работают реальные пользователи

*В AI Advisory Intake Assistant:* Vercel автоматически создаёт preview-ссылку для каждого pull request. Production — это финальная ссылка.

---

**Environment variable (переменная окружения)**

*Аналогия:* Конверт с секретом, который сервер открывает при запуске. Приложение знает, где искать конверт, но сам конверт не лежит в коде.

*Определение:* Переменная, которая хранится не в коде, а в настройках сервера или платформы. Используется для хранения API-ключей, паролей и других секретов.

*Пример:*
```
SUPABASE_URL=https://abc.supabase.co
ANTHROPIC_API_KEY=sk-ant-...
```

*В AI Advisory Intake Assistant:* Ключ от Anthropic API никогда не лежит в коде. Он хранится в переменных окружения Vercel.

---

**Secret (секрет)**

*Аналогия:* Ключ от сейфа. Нельзя написать его на стикере и приклеить к сейфу.

*Определение:* Любые чувствительные данные, которые нельзя хранить в открытом коде: API-ключи, пароли от базы данных, OAuth-секреты.

*Правило:* Secrets никогда не попадают в GitHub. Никогда не вставляются в промпты AI в открытом виде. Хранятся только в переменных окружения.

---

**CI/CD** (Continuous Integration / Continuous Deployment)

*Аналогия:* Конвейер на заводе: как только деталь готова — она автоматически проверяется и передаётся дальше. Человек не делает это руками каждый раз.

*Определение:* Автоматизированный процесс сборки, тестирования и деплоя приложения при каждом изменении кода. Vercel запускает CI/CD автоматически при merge в основную ветку.

*В нашем учебнике:* Когда вы делаете merge в `main`, Vercel автоматически публикует новую версию приложения.

---

### Группа 7. Agent, tool, hook, prompt

---

**Prompt (промпт)**

*Аналогия:* Инструкция для стажёра: чем точнее и конкретнее — тем лучше результат.

*Определение:* Текстовое сообщение, которое вы отправляете AI-инструменту, чтобы получить нужный результат. Качество промпта напрямую влияет на качество ответа.

*В нашем учебнике:* В каждой главе есть готовые промпты для работы с Lovable, Claude, ChatGPT и Claude Code.

---

**Agent (агент)**

*Аналогия:* Помощник, которому вы дали задание и инструкции. Он выполняет шаги самостоятельно, принимает промежуточные решения, но возвращается к вам за подтверждением в ключевых моментах.

*Определение:* AI-система, которая может выполнять многошаговые задачи, используя инструменты (tools): читать файлы, вызывать API, писать код, запускать тесты. Агент принимает решения в рамках заданных правил.

*В нашем учебнике:* Claude Code — агент для кодинга. Вы даёте ему задачу, он выполняет шаги, вы проверяете результат.

---

**Tool (инструмент агента)**

*Аналогия:* Инструмент в наборе помощника. У агента может быть «инструмент поиска», «инструмент записи в файл», «инструмент вызова API».

*Определение:* Функция, которую агент может вызывать для выполнения действий. Агент сам решает, какой инструмент использовать в зависимости от задачи.

*Примеры tools Claude Code:* Read (прочитать файл), Write (записать файл), Bash (запустить команду), Grep (найти текст в коде).

---

**Hook (хук)**

*Аналогия:* Триггер — «когда происходит X, выполни Y». Как правило в офисе: «Когда приходит клиент — автоматически оповестить менеджера».

*Определение:* Механизм, который запускает определённое действие при наступлении события. В Claude Code хуки позволяют выполнять проверки или действия автоматически (например, до или после того, как агент делает коммит).

*В нашем учебнике:* Главы 22–23 объяснят, как настроить хуки для агентной разработки.

---

**CLAUDE.md**

*Аналогия:* Корпоративный регламент для нового сотрудника: «Вот наши правила, стандарты и контекст проекта».

*Определение:* Специальный файл в корне проекта, который даёт Claude Code контекст о проекте, правила работы и ограничения. Агент читает этот файл и следует его инструкциям.

*В AI Advisory Intake Assistant:* В главе 22 мы напишем CLAUDE.md, который объясняет агенту структуру нашего приложения, какие файлы трогать нельзя и как делать коммиты.

---

**Subagent (подагент)**

*Аналогия:* Помощник помощника. Старший агент делегирует конкретную задачу подагенту, который специализируется на ней.

*Определение:* Агент, запущенный другим агентом для выполнения конкретной подзадачи. Позволяет параллельно выполнять независимые задачи.

*В нашем учебнике:* Claude Code может запустить подагента для тестирования, пока основной агент занимается рефакторингом.

## 8. Типовые ошибки новичка

### Ошибка 1: «Я не знаю этот термин — значит не могу работать с инструментом»

**Симптом:** Читатель останавливается на незнакомом слове и ждёт, пока «всё станет понятно».

**Почему возникает:** Ощущение, что нужно понять всё сразу.

**Чем опасна:** Потеря темпа. Незнакомые термины будут всегда — это нормально для любой профессии.

**Как исправить:** Записать незнакомый термин, задать вопрос AI по промпту из этой главы, идти дальше. Понимание приходит через практику, а не через дочитывание глоссария.

**Как проверить:** Вы смогли задать вопрос AI и получить понятный ответ за 2 минуты.

---

### Ошибка 2: Путать authentication и authorization

**Симптом:** Настроен вход в приложение, но все пользователи видят все данные.

**Почему возникает:** Кажется, что «вход» = «ограничение доступа». Это не так.

**Чем опасна:** Утечка данных. Сотрудник А видит запросы сотрудника Б.

**Как исправить:** Помнить: authentication = «кто вы», authorization = «что вам можно». Авторизация настраивается через RLS (глава 12) и роли пользователей.

**Как проверить:** Войти под тестовым пользователем А и убедиться, что он не видит данные пользователя Б.

---

### Ошибка 3: Хранить secrets в коде

**Симптом:** API-ключ написан прямо в коде приложения: `const apiKey = "sk-ant-..."`.

**Почему возникает:** Проще написать ключ прямо там, где он нужен.

**Чем опасна:** Если репозиторий публичный — ключ виден всем. Даже в приватном репозитории ключ попадает в историю коммитов.

**Как исправить:** Всегда хранить secrets в переменных окружения. Глава 15 полностью посвящена этой теме.

**Как проверить:** Команда `grep -r "sk-ant-" .` в корне проекта не находит ничего в файлах кода.

---

### Ошибка 4: Коммитить всё подряд одним большим коммитом

**Симптом:** Один коммит с сообщением «все изменения» или «fix» содержит 20 разных изменений.

**Почему возникает:** Кажется, что история коммитов — это формальность.

**Чем опасна:** Если что-то сломается — невозможно понять, какое именно изменение сломало. Откат одного изменения становится невозможным без потери всего остального.

**Как исправить:** Один коммит — одно логическое изменение. «Добавил форму ввода», «Подключил Supabase», «Настроил RLS». Подробнее — в главе 7.

**Как проверить:** Прочитайте последние 5 коммитов в репозитории. Понятно ли из сообщений, что было изменено?

## 9. AI помогает / AI не должен / Human review обязателен

### AI помогает
- Объяснить любой термин из глоссария с примером из вашего проекта
- Найти аналог незнакомого технического понятия в бытовом языке
- Проверить, правильно ли вы поняли концепцию
- Написать простое объяснение технического термина для коллеги
- Найти ошибку в тексте технической конфигурации

### AI не должен
- Придумывать термины или их значения без опоры на документацию
- Утверждать, что конкретная конфигурация безопасна без проверки
- Принимать решения об архитектуре на основании терминов без контекста проекта

### Human review обязателен
- Проверить, что понимание RLS и auth соответствует реальной конфигурации Supabase
- Убедиться, что secrets не попали в код (перед каждым commit)
- Проверить, что commit messages внятно описывают изменения
- Подтвердить, что pull request проверен живым человеком перед merge

## 10. Минимум безопасности и качества

Три правила, которые вытекают из этой главы:

**Правило 1. Secret не равно environment variable — но должно храниться там.**
Secret — это ценность (ключ, пароль). Environment variable — это контейнер. Всегда помещайте secrets в переменные окружения, а не в код.

**Правило 2. Authentication без authorization — это полумера.**
Если вход настроен, но RLS не настроен — данные открыты всем залогиненным пользователям.

**Правило 3. Commit без понятного сообщения — потерянная история.**
Через месяц вы не вспомните, что делал коммит «fix». Пишите сообщения так, будто объясняете коллеге, который видит репозиторий первый раз.

> В этой главе мы делаем учебный минимум. Это не полноценный security review. Для корпоративного применения нужен отдельный human review.
